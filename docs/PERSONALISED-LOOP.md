# Personalised learning cycle and operations

A reviewed practice bank belongs to one exact programme content hash, one selected activity and one learner. Muse Wonder Standard authors four distinct questions; deterministic validation binds canonical sources. Human review checks meaning and answers. The reviewer sees the key, so no claim of unseen assessment is made. The existing NCB identity, Origin, epoch leases and version checks protect progress.

The server preserves each first answer and help separately. A wrong answer requires a reviewed explanation before the next question. Practice and transfer use different prompts; one later question opens after one day if any earlier answer was wrong/uncertain or supported, otherwise three days (all three answers also require reported confidence). These are fixed study heuristics, not validated memory predictions. A completed cycle recommends another objective or fresh cycle. Game wins and free explanations remain ungraded. Preferences affect generated wording/examples; changing them preserves the existing reviewed bank and offers new generation.

Progress lives in existing learner_profiles slots. Export, deletion and progress retention cover these slots. Removing an episode or programme does not erase separate progress; use Your data to delete all learning records. No new NCB table or identity flow.

## Costs

D1 cost_receipts records one content-free receipt per submitted provider operation. Meta Responses usage includes input/output and optional cached input tokens, including invalid completed output. Fish success records exact UTF-8 input bytes and output audio bytes; interrupted transfers remain unknown. Edits, review and saved playback do not create receipts. Rates are snapshotted: COST_META_INPUT_PER_M, COST_META_CACHED_PER_M, COST_META_OUTPUT_PER_M, COST_FISH_BYTES_PER_M. Defaults verified 2026-11-01: USD4/0.20/20 per million tokens and USD15 per million UTF-8 bytes. Invalid rates make estimates unknown. Missing cache breakdown uses the full input rate and is labelled. Provider credits/discounts and historical untracked requests are excluded. R2 bytes are capacity, not a storage invoice; operation and hosting costs are excluded. Receipts expire after 30 days; learner deletion unlinks the learner but retains a workspace cost receipt until expiry.

## Background retention

Only authenticated learner requests register a subject. The first authenticated request pins the private workspace identity in D1; later enrollments must match it, and every background query is restricted to that identity. The maintenance writer has no IDs, policies or user content input. It applies existing saved policies, resumes previously requested cleanup, checks R2 absence and real NCB deletions, and retains failed-provider cleanup for retry. Five oldest-checked subjects per pass; leases prevent overlapping passes. A saved receipt reports bounded content-free failure codes and processed/failed/pending and whether more subjects remain. On-access retention remains a fallback. New registrations are automatic; legacy learners without a known workspace mapping register at their next authenticated visit.

Unattended access uses the owner-private Sites platform boundary and RETENTION_BACKGROUND_ENABLED=true. Never enable this shared writer on a public/shared deployment. The linked cloud task must read get_site, verify owner role, custom access with exactly the owner and no groups/external visitors, then obtain its fresh service-access token. It sends the token only to this Site in OAI-Sites-Authorization. It sends POST /api/maintenance with X-Mosaic-Maintenance: retention-v1 and an empty body, then GETs the same route to verify lastRun.runId. No visitor headers are invented. If more=true, repeat sequentially up to 20 passes; report attention or an incomplete sweep. On a timeout, GET status before another POST; a held lease returns409. If audience changes, do not invoke; report. No republishing, new generation, retention changes or source edits during scheduled runs.

The schedule should run daily at 03:15 Europe/London. Until linked schedule creation and intended-access readback are verified, background deployment is incomplete. A successful schedule creation alone is not proof it ran.
